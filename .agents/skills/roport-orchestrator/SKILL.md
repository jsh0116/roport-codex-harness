# RO:PORT 개발 오케스트레이터

목표는 요청 기능의 코드·양쪽 인터페이스·관련 검증을 함께 완성하는 것이다.
로봇·모델·Cloud 서비스를 새로 만들거나 구동하는 권한은 이 스킬에서 생기지 않는다.

개인 하네스의 원본은 별도 checkout에서 관리하고 이 스킬·역할은 제품에 로컬 설치한다. 제품의 추적 파일은 설치기가 수정하지 않는다. 제품 작업은 제품 프로젝트에서 시작한 채팅에서 수행한다.

## 맥락과 입력

1. 루트와 대상 모듈의 `AGENTS.md`, 현재 branch/status, 호출부·manifest·lockfile·CI를 먼저 확인한다.
2. 연동·설계 변경에는 [프로젝트 맥락](references/project-context.md)을 읽는다. 과거 세션 결정은 출처와 확인일이 있는 참고 정보다. 관련 최신 Confluence Tech Spec과 실제 구현을 대조하고 차이를 기록한다. 접근이 막히면 미확인 범위를 명시한다.
3. 관측 단위·시간 기준·좌표계·모델/캘리브레이션 버전·명령 소유자와 완료 판정을 확인한다. 미정 timeout·도킹 오차·관절 제한에 임의 기본값을 넣지 않는다.

## 역할과 경계

[전문 엔지니어 배정](references/engineering-roles.md)을 읽고 구현 분야에 맞는 `.codex/agents/roport_*.toml` 역할을 선택한다.
설계, Pinky, OMX, 인지, 모방학습, 관제, fleet planning, AI, 서비스, 웹, HMI, 하드웨어, 로봇 검증, 플랫폼, 보안의 전문 역할 15개가 있다.
탐색은 `harness_explorer`, 경계 설계는 `harness_architect`, 독립 검토는 `harness_reviewer`, 검사는 `harness_qa`를 재사용한다.
분야가 특정되지 않는 작은 구현에는 `harness_worker`를 사용할 수 있다. 전문 엔지니어와 같은 파일을 중복 배정하지 않는다. 필요한 역할만 실행한다.
요구사항·명세 간 책임이 다르면 시스템 아키텍트로 적용 범위를 확인하고 부모가 공통 계약을 정한다. 일반 QA와 로봇 통합 검증, 일반 코드 리뷰와 보안 리뷰를 같은 파일 수정자로 동시에 배정하지 않는다.

부모가 계획·공유 schema·lockfile·설정·최종 통합을 소유한다. 워커에게는 경로가 겹치지 않는 파일 소유권을 준다. 생산자와 소비자가 같은 계약에 의존하면 계약을 먼저 확정하고 독립 구현을 병렬화한다.
부모가 위임할 때 이 스킬과 관련 하위 `AGENTS.md` 경로를 작업 패킷에 넣는다. 제품 수정은 워커가, 재현·검증은 QA가 맡는다. 자식은 추가 위임 없이 분할 필요를 부모에게 알린다.

현재 Codex에서 에이전트의 권한은 부모를 상속한다. seed TOML의 `sandbox_mode`는 역할 의도의 기록이며 강제 격리를 보장하지 않는다. 탐색·리뷰에는 쓰기 금지 지시를 적용하고 실제 세션 권한을 확인한다. 모델·추론 수준은 역할 TOML의 명시값을 따른다. 호출 전 역할 파일을 읽고 [모델 선택과 예외 처리](references/engineering-roles.md#모델-선택과-예외-처리)를 적용한다.

## 여러 모듈 작업 실행

실행 장부·통신·재개에는 [기본 런타임 가이드](../harness/references/runtime-guide.md)를 읽는다.

1. 작은 작업이면 직접 수정하고 관련 검사로 끝낸다. 독립 작업·인계·재개가 필요한 변경이면 실제 요구사항으로 plan 파일을 만들고 `run.py init`을 실행한다. `inputs`에는 고정 참조, `ownership`에는 수정 경로, `dependencies`에는 선행 작업을 넣는다. 같은 파일을 inputs와 ownership에 겹쳐 넣지 않는다.
2. 각 작업에 목표·관련 Jira·완료 기준·검증 명령·중요 결정과 필요한 스킬을 기록한다. 공유 계약 변경은 부모가 통합한다. `task-<id>/input.md`가 실제 생성된 경로인지 확인한다.
3. 현재 세션이 이 프로젝트 루트에서 시작됐는지 확인한다. 첫 대기 자식의 실제 생성 응답을 받은 뒤 실제 ID로 `run.py start`를 실행하고 최신 패킷을 전달한다. custom role을 선택할 수 없으면 정의를 읽어 사용 가능한 기본 역할에 전달하고 대체 실행으로 기록한다.
4. 준비된 독립 작업만 실행하며 설정상 최대 자식 3개와 실제 도구 슬롯 중 작은 한도를 따른다. 부모는 공용 계약·통합을 진행한다. 같은 파일·빌드 캐시를 쓰는 작업은 순차 실행한다.
5. 중요한 발견·질문·차단·인계는 `communication.py`로 기록하고 실제 협업 도구로 전송한다. 기록·전송·응답을 구분한다. 읽기 전용 역할의 기록은 부모가 대신 남긴다. 이 절차는 현재 실행의 서브에이전트 통신에 적용하며 다른 사용자 채팅이나 Slack에 메시지를 보내는 권한을 주지 않는다.
6. 실제 결과를 `run.py result`로 등록하고 실제 idle/stop 응답을 확인한 뒤 세션 상태를 기록한다. 결과 완료와 세션 종료는 별개다. 파일 소유권은 이전 작성자의 유휴·중단 확인 후 넘긴다.
7. [검증 절차](references/verification.md)에 따라 모듈 검사와 생산자/소비자 경계를 확인한다. 필수 실패는 기본 2회 이내 수정·재검증하고 남은 실패를 명시한다. 해당 run은 `validate.py --project . --run RUN_ID --complete`로 근거와 최신성을 확인한다.

자식 생성이 ID 없이 실패하면 추가 생성을 멈추고 부모가 가능한 작업을 순차 수행한다. 오류 원문과 대체 작업을 기록하고 미시작 native task를 성공 처리하지 않는다.
입력 내용 변경은 `resume --run OLD --new-run NEW`, 목표·결정·소유권·완료 기준 변경은 수정한 `--plan-file`도 함께 전달한다. 이전 실행은 보존하고 영향받은 후속 작업을 다시 검증한다.

## 완료 보고

요청 기능의 실제 변경, 검사 명령·결과, 남은 실패/미실행 항목을 보고한다. 정적 검사·mock/단위 테스트·시뮬레이션·실장비·Cloud를 구분한다. 원격 push/CI를 확인하지 않았다면 로컬 확인 범위를 밝힌다. 실제 Jira 없이 티켓 번호를 만들거나 관련 없는 티켓으로 커밋하지 않는다.
